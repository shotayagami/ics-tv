## 設計方針

- スタック（2026-09 現在の実装）:
    - **studio.\***: 管理 React SPA（`frontend/apps/studio`）。StudioPage 共通シェル + 左サイドバー 5 グループ。Django session 認証（`SessionAuthIsStaff`）で django-ninja JSON API を呼ぶ。
    - **ops.\***: 運行（放送当直）用 React SPA（`frontend/apps/ops`）。🔴放送コンソール + タイムキーパー（[ui-operations.md](ui-operations.md) / [timekeeper-live.md](timekeeper-live.md)、分離方針は [refactor-service-split.md](refactor-service-split.md)）。
    - **公開面（tv.\*）**: Django SSR + React 島 5 本（`home` / `guide` / `discover` / `detail` / `player`）+ Bootstrap バンドル（`bootstrap-public`。管理側は `bootstrap-admin`）。`web` は Phase 0 の SPA 足場。
    - **意図的な Django テンプレ据え置き**: フォーム系の一部（編成フォームの下位画面・素材/CM/キューシート編集等、`server/scheduling/urls.py`・`server/medialib/urls.py` 配下）は Django テンプレのまま残す判断（React 移行 Phase 2d の確定事項）。
- 中核 2 画面: 編成タイムライン（運用者がフリー編成で番組を任意時刻に配置）と公開番組表（視聴者向け）。レイアウトの作り込みが直接の価値になるため、本書で重点的に設計する。
- 周辺画面: リアルタイム送出コントロールは安全性が要るため ops.\* に分離した専用設計（[ui-operations.md](ui-operations.md)）。素材・CM 管理は admin 寄りの CRUD として機能優先で設計する。YouTube／枠管理は API 操作の誤りが送出断に直結するため確認フローを明示する。
- 本書の位置づけ: 画面の情報設計の記録。ナビ/ルートと権限の正本は実装（`nav.ts` / `App.tsx` / `server/api/auth.py`）。

## ASCII の視覚言語（凡例）— 全画面共通

ワイヤーは等幅・box-drawing 文字（`─│┌┐└┘├┤┬┴┼` 等）で描き、表示幅は約 96 桁に統一する。表示幅は CJK（全角）= 2 桁、box-drawing・記号・ASCII = 1 桁で数える（モバイル枠など一部は内寸を明記して別幅とする）。各画面で以下の記号体系を一貫して用いる。

- 番組種別: `◇` recorded（録画）／`◆` live（生）。公開系では `REC` ／ `●LIVE` のテキストバッジを併用する。
- タイムライン素材帯: `▓` ad_break（CM 枠）／`░` filler（隙間充填ループ）／`▤`・`SLATE` slate（スレート）／`▒` ロード中スケルトン（`░` filler と区別する灰色）／`▞` ドラッグ中ゴースト。
- normalize_status バッジ: `●ready`（送出可）／`◐processing`（正規化中・進捗 %）／`○pending`（待機）／`✕failed`・`failed`（失敗）。
- yt_slot_status バッジ（YouTube 枠）: `[.]created`（bind 待ち）／`( )ready`／`(~)testing`／`[*]live`／`[v]complete`／`[!]error`。
- playout_status: `scheduled` ／ `executing` ／ `● done` ／ `⊘ skipped` ／ `! failed`。
- CM 在庫状態: `●配信中` ／ `○予定` ／ `✓終了` ／ `上限到達`（aired_count ≥ max_airings）／`⚠残少`（残比率 < 20%）／`△要設定`（campaign 日付 NULL）。
- 注意・危険: `!`・`⚠` 要注意（配置済みだが送出に支障し得る）／`◆` 要確認操作／`◆◆` 二段確認（文字列一致が必要）。
- ヘルス: `●OK` ／ `●NG` ／ `───` 該当なし・取得不可。
- 操作の有効性: 文末の `(無効)` `(非活性)` `(要確認)` で活性条件を示す。`[ ... ]` はボタン、`[ ▼ ]` はセレクタ、末尾 `...` は確認ダイアログを開く操作。

凡例の記号は各画面のワイヤー内でも要所に再掲し、自己説明性を保つ。サブシステム固有のバッジ（納品の `delivery_status`／`qc_verdict`、請求の `◎`=代理店宛 など）は各 companion doc 冒頭の「視覚言語の追補」に定義し、本書の凡例を基底語彙とする。

## 情報設計（IA）・共通レイアウト

studio.\* の全画面は StudioPage 共通シェル（左サイドバー＋メイン領域）に各画面のワイヤーを嵌め込む構成とする。サイドバーのグループ/項目は `frontend/apps/studio/src/nav.ts` の **5 グループ＋ホーム**が単一正本であり、ダッシュボード（`/`）のランチャも同じ定義を参照する（宛先ドリフト防止）。

旧設計の「グローバルヘッダ 8 区分ナビ（編成/運用/営業/納品/素材・CM/YouTube/公開/設定）」は廃止した:

## 編成タイムライン（運用者・中核）

フリー編成：番組（program）を任意時刻に縦タイムラインへ配置し、番組間の隙間は既定フィラー（channel.default_filler_id）のループで自動充填する。同一 channel での時間的重なりは DB の `EXCLUDE USING gist` 制約で禁止され、24h を黒画面にしない。時刻軸直下に薄い「YT 枠帯」を置き、`youtube_slot.status` を read-only で可視化する（詳細操作は YouTube／枠の画面に委譲）。各 start_at/end_at は timestamptz のローカル表示であることを明示するため `JST` を付す。

主要インタラクション（実装: `frontend/apps/studio/src/pages/TimelinePage.tsx` / `server/scheduling/edit_views.py`）: ドラッグ＆ドロップは start_at 変更（移動は録画/生とも尺固定）で、確定時に `POST /scheduling/ch/<slug>/programs/<id>/move/`（body: `start_at`）へ POST する。端ハンドルのリサイズは `POST /scheduling/ch/<slug>/programs/<id>/resize/`（`end_at`）、CM 枠の位置調整は `POST /scheduling/ch/<slug>/adbreaks/<id>/move/`（`offset_ms`）。重なり（EXCLUSION 相当）はサーバ側検証で **422 + `{ok:false, error:"overlap", earliest:…}`** を返し、タイムラインは赤表示＋配置可能な最早時刻を提示する。旧設計の事前検証 API（`POST /program/validate`）は存在しない — 判定はドロップ確定時のサーバ応答で行う。保存経路（番組編集フォームの [保存]）も同じ検証に通る。

注記:
- end_at は scheduler 不変条件 `end_at = start_at + asset.duration_ms + Σ(ad_break.duration_ms)` と対応させ、録画は自動算出（編集不可）とする。
- 生（live）の end_at は手入力（chk_time: end_at > start_at）。次番組 start_at が end_at より前なら実行時に強制カット（scheduler 既定）であり、配置自体は許容する。
- normalize_status が pending/processing/failed の asset は編集ペインで選択不可（保存ブロック）。配置後に再正規化が走行中の録画は状態G で `!` 表示し、ready にならなければ当該区間は SLATE になる旨を警告する（scheduler の critical → goto_slate と整合）。
- ad_break の充填は 15s/20s グリッドの整数倍を強制（chk_grid_multiple）。有効 cm_creative（campaign 期間・max_airings/aired_count・normalize_status=ready で絞り込み）が不足する枠は、**埋まらない残尺を既定フィラー（`PLAY_FILLER`, reason=cm_insufficient）で充填**する（house_cm／SLATE 代替は不採用。[scheduler.md](scheduler.md)「CM枠の充填」）。充填プレビューは保存時点の見込みであり、実送出時に scheduler.fill_break が再評価する。
- 生（live）の CM は ad_break 不可。cm_bundle を事前登録し、運用画面の「CM IN」で割り込む（play_cm_bundle）。
- public_visible=false の番組は `internal(非公開)` と表示し、公開番組表に出ない旨を区別する。

## 公開番組表（視聴者向け）

視聴者向けの公開ページ。掲載は public_visible=true の番組のみで、並びは program.start_at 昇順・選択 CH（channel_id）で絞る。送出機構名（フィラー等）は視聴者面に露出しない（ただし `rerun_eligible` を立てたフィラー素材のみ「再放送」として表示投影される）。

**再生経路（実装正）**: サイト内プレイヤーの主経路は**自前 HLS**（送出ノード MediaMTX 起点 + hls.js。HLS 署名トークンでゲートし、`hls_url` は entitled 時のみ API が返す）。**YouTube iframe 埋め込みは entitled 時のみの縮退フォールバック**である — `frontend/apps/player/src/VideoPlayer.tsx` は `hlsUrl → youtubeBroadcastId(iframe) → placeholder` の順で出し分け、`server/api/routers/player.py` は entitled でないとき `youtube_broadcast_id` を返さない（会員/FC ティア ゲートの素通り防止）。旧設計の「`youtube_slot.status='live'` の watch URL へ誘導（枠ごとに URL が変わるためページ側で追従）」は主経路ではなくなった。YouTube 側で視聴し続ける導線は rolling 枠（[youtube.md](youtube.md)）の説明欄/チャット誘導が担う。

以下 A〜E のワイヤーは初期設計（YouTube 埋め込み前提）。CTA・プレイヤー枠は上記の実装正で読み替える（例:「YouTubeで視聴 ↗」→ サイト内 HLS 再生 + 画質/音声のみ切替）。

## YouTube／枠

YouTube Data API v3 で、永続 liveStream（RTMP キー）の上に liveBroadcast（既定 4h 枠、`youtube_config.slot_minutes=240`）を rolling 生成・遷移する。永続キー・OAuth・枠設定は本画面（チャンネル設定 → YouTube）で管理し、枠の状態確認と手動操作は枠ダッシュボードで行う。送出スレート・now-playing・CM IN は運用画面の責務であり、本 2 画面には持ち込まず参照誘導に留める。非可逆操作（今すぐ complete／強制 transition）は確認必須・取消不可を明示し、transition は stream active のときのみ活性化して error の量産を抑止する。永続キーの [ローテ] は**送出ノード側 encoder env（`/etc/icstv/encoder-<slug>.env` の `CF_INGEST_URL`＝YouTube ingest URL＋キー連結。変数名は historical）を手動更新しないと送出断になる**ため確認必須とする（本線は YouTube 直 push で CF Live Output とは無関係 — [youtube.md](youtube.md) §本線 egress。なおローテ操作自体は現状未実装のワイヤーフレーム構想）。

## 確定した運用判断（2026-06-09）

1. **生番組ドラッグの挙動**: 本体ドラッグ＝丸ごと移動（duration 維持）、端ハンドルドラッグ＝リサイズ。
   録画・生で挙動を統一し、生の尺変更は端ハンドルまたは編集フォームの end_at 手入力で行う。
2. **YouTube 枠 手動操作の権限**: 枠操作（transition／complete／再作成）は**運用者に全開放**（全操作に要確認、
   再作成は二段確認）。OAuth 接続・永続キー作成/ローテは**管理者限定**。
3. **2h 境界を跨ぐ録画のアーカイブ**: 通常は単一リンク。境界を跨いだ番組**のみ**自動で
   「アーカイブ（前半/後半）」を分割表記する。あわせて編成段階で 2h 境界に寄せ跨ぎを抑制する運用を推奨。
4. **公開番組表のフィラー露出**: 番組は**実放送時刻を維持**し、隙間は淡色の「ブレーク」帯（尺は控えめに表示）。
   EPG の時刻信頼性を優先し、非表示で番組間を詰める案は不採用。

## 未確定・論点

- マルチ ch（最大 4）対応時、EXCLUSION は channel_id 単位で問題ないが、ch 切替時に YT 枠帯も ch 連動で差し替える必要がある。Phase 1 は 1ch（overview 意思決定 #11）であり、channel が 1 件の間は ch セレクタを非表示にする実装余地を残す。
- cm_creative.aired_count による在庫枯渇の充填プレビューは保存時点の見込みであり、実送出時に scheduler.fill_break が再評価する。予測である旨をツールチップ等で補足する。aired_count の増分タイミング（予約時 vs 実送出時）は scheduler 上「実送出確定時」とする（datamodel.md の論点に対応）。
- 表示幅は CJK=2・box-drawing/記号=1 の前提で 96 桁に揃えている。曖昧（East-Asian Ambiguous）幅の記号はレンダラ依存で見え方が変わり得るため、実環境の等幅フォントで最終確認する。
- 生退避ミュート（MIXER 1-11 VOLUME 0）の要否、OSC の file/time アドレス綴り・引数単位は CasparCG の版依存であり、実機で確定する。
