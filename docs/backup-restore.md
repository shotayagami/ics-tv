# バックアップと復旧

本体の PostgreSQL をバックアップ・復元するときの手順と、確かめた挙動、復旧の判断で注意すべき点を記す。
このリポジトリは定期バックアップを提供しない (取得・外部保管・成否の監視は導入者の責任)。
以下の挙動は、合成データだけを入れた使い捨ての PostgreSQL で実際に確かめたものである
(`tools/m2_restore_rehearsal.py`。配布物には含まれず、準備側のリポジトリにある)。

## 何を保管するか

| 対象 | 内容 | 備考 |
|---|---|---|
| PostgreSQL (本体 DB) | 会員・購読・在籍・精算・編成・素材のメタデータ・番組表など全て | `pg_dump -Fc` |
| オブジェクトストレージ | 素材・アップロード・字幕などの実体 | DB は `r2_key` などの**参照**だけを持つ。実体との対応は DB のダンプだけでは確かめられない |
| `ICSTV_FIELD_ENCRYPTION_KEY` | DB の暗号化フィールドの鍵 | **ダンプとは別の場所に、別の権限で保管する**。失うと暗号化フィールドは復号できない |
| `ICSTV_HLS_SIGNING_KEY`・`DJANGO_SECRET_KEY` | 視聴トークンの署名・セッション等 | 失っても再発行できるが、発行済みのトークン・セッションは無効になる |
| Stripe の署名秘密 (`STRIPE_WEBHOOK_SECRET` / `STRIPE_FC_WEBHOOK_SECRET`) | Webhook の検証 | Stripe 側で再発行できる |

暗号化フィールドは、送出ノードの認証トークン (`agent_token`)、YouTube の配信キー・OAuth 資格情報、
会員の 2 段階認証の秘密、SRT のパスフレーズ、ファンクラブの配信先ストリームキーである。

## 取得と復元

```sh
# 取得。出力先は -f で指定する
pg_dump -Fc -f icstv.dump "$DATABASE_URL"
pg_restore --list icstv.dump > /dev/null    # アーカイブが読めること

# 復元 (空のデータベースへ)
createdb icstv_restored
pg_restore --no-owner -d icstv_restored icstv.dump
```

復元した DB を指して、次の 2 つが通ることを確かめる。

```sh
python manage.py migrate --check                     # 未適用の migration が無い
python manage.py makemigrations --check --dry-run    # モデルと復元したスキーマが一致する
```

## 暗号化フィールドと鍵

- ダンプには暗号文しか入らず、平文の秘密は含まれない (確認済み)。**鍵はダンプと同じ場所に置かない。**
- 鍵が**違っても、鍵が無くても、例外は出ない。** 読み出しは、復号できなかった値を、暗号文 (`enc:v1:` で始まる文字列) のまま返す。
  「エラーが出なかった」は成功の証拠にならない。**復元後は、既知の値と突き合わせる**。たとえば
  `Channel.objects.get(slug="<slug>").agent_token` が、控えてある値と一致すること。`enc:v1:` で始まる値が返るなら、鍵が違う。
- 鍵を設定せずに保存した値は平文で保管される (開発用)。配布向けの設定 (`ICSTV_DISTRIBUTION_MODE`) は鍵の設定を要求する。

## 書き込みの後の復旧

- **ダンプ以降の書き込みは、ダンプを復元しただけでは戻らない。** 単純な巻き戻しは、その間の会員登録・購読・精算を失う (確認済み)。
  巻き戻す前に、停止 → 照合 → 再適用または前進修正のどれで直すかを決める。判断者・保持期間・観測期限は導入者が決める。
- 課金の状態は Stripe が真実で、Webhook の処理は `event.id` で冪等である。**ダンプ以降の Stripe のイベントを再配送すれば、
  復元した DB は元の状態へ収束する。既に適用済みのイベントの再配送は何も変えない** (確認済み。
  イベントの再配送は Stripe 側の再配送機能で行う。再配送できる期間は Stripe の仕様に従う)。
- **順序を保たない再配送は収束しないことがある。** たとえばチャージバックの通知が、対応する精算の記録より先に処理されると、
  その状態は失われる (`docs/operations.md`「Stripe 連携の既知の制約」)。イベントは発生順に再配送する。
- Stripe 以外の書き込み (会員登録・コメント・アップロード・編成の編集など) には、再適用できる記録が無い。
  ダンプ時点より後の分は、別の手段で作り直す。

## 復元後の確認

1. `migrate --check` と `makemigrations --check --dry-run` が通る。
2. 暗号化フィールドを既知の値と突き合わせる (上記)。
3. 会員数・有効な購読数・精算の件数と最新の日時を、控えと比べる。
4. 素材の `r2_key` の一覧が、ストレージに実在するオブジェクトと対応する (DB だけでは確かめられない)。
5. Stripe のダンプ以降のイベントを、発生順に再配送する。
