# 要件

## 背景・経緯

YouTube配信が流行している。もともと **circle-ics.com** として YouTube配信を行っており、
当時は OBS を使用した手動配信が主だった。これを **24時間自動配信** になるよう、Webシステムを
構築したい。**ウェザーニューズ社の仕組み**（ウェザーニュースLiVE / SOLiVE）を参考にする。

## 機能要件

### 配信コンテンツ
- 基本は録画番組。
- 生番組と録画番組を同時登録できる。

### CM
- CM枠を設定できる（**15秒スパンと20秒スパン**に対応）。
- 生番組の場合は CM を事前にバンドルし、任意タイミングで流せる。

### 配信基盤
- YouTube は配信枠の概念があるので、**2時間 × 12枠** の自動枠取得機能を付ける。
- Cloudflare 側の配信の仕組みも使用する。

### 公開・収益
- 番組表を Web 公開できる。
- サブスク配信にも対応（この場合は **Cloudflare のみ**）。

### 規模
- チャンネル数は最大 4 とし、それぞれ配信できる。

## 追加要件

### スコープ・フェーズ（当初要件の具体化）

当初の「規模」「公開・収益」を運用フェーズに分けて具体化した。
- **Phase 1 は 1ch・生番組まで**を対象とする（録画＋生＋CM）。全機能を 1ch で検証してから最大 4ch へ複製する（決定 #4 / #11）。
- **サブスク配信（Cloudflare 経路の有料視聴）は Phase 2 以降**。CF 経路は Phase 1 で送出系として先行構築するが、視聴ゲート・課金は対象外（決定 #12）。
- 配信は **YouTube＝無料公開／自社(CF)経路＝有料** の二系統という整理（ウェザーニュースLiVE / SOLiVE と同構造）。

### 素材納品ポータル（#15）

制作側が完パケ素材を**オンラインで納品**し、運用側が一元管理するワークフローを新設する（TBS「メディアブランチ」相当）。当初は admin が手でレコードを起こしていた素材入口を、ポータル化する。詳細設計は [delivery.md](delivery.md)。
- 制作側がブラウザからアップロード納品し、**プレビュー・QC・納品状況の可視化・キューシート出力**まで行う。
- **外部制作会社にも開放**し、組織スコープの RBAC で社内ポータルと分離する。
- 対象は**全用途**（本編 / 配信 / 番宣 / 番販 / 保管）を用途軸で一元管理する。
- QC は**技術チェック＋ R128 ラウドネス測定＋リーダー（カラーバー / トーン / 無音）検出**。
- 継ぎ目の一貫性のため、mezzanine で**ラウドネスを -14 LUFS（配信基準）に強制統一**する。

### 営放サブシステム：広告出稿・請求精算（#16）

当初要件の「CM 枠設定／生番組のバンドル CM」を、民放の営業放送システム（営放）相当の商流まで拡張する。詳細設計は [sales.md](sales.md)。
- **タイム（番組提供）契約とスポット契約**の両対応。代理店マスタ＋手数料率（NULL＝直販）。
- **契約駆動の CM 割付**：業種競合排除（同一枠／隣接枠）・線引き（時間帯指定）・指定番組割付。考査（業態考査 / 表現考査）ゲートを契約割付に適用。
- **放送実績の台帳化（放確）**と、**月次締め・放送確認書・請求書（インボイス制度対応）・入金管理**を内製。
- 料金は本数×単価（タイムランク別料金表）で算定。GRP / パーコストは視聴率データが無いため対象外。
- 24/7 送出系の安全性を最優先し、**営放が無くても従来の均等ローテ送出が動くこと（疎結合）**を要件とする。

### 運行・監視：APC 運用機能（#17）

24/7 運用の堅さを担う運行・監視機能を実装する（実放送局の APC・マスター運行相当）。詳細設計は [operations.md](operations.md)。
- **フィード断の自動退避・自動復帰**：生番組のフィード断時にスレートへ自動退避し、復帰はヒステリシス付きで自動判定（フラップ多発時は自動復帰を停止し手動フォールバック）。
- **運行ダッシュボード**：now-playing・レイヤ状態・ヘルス・AS-RUN ライブログをリアルタイム監視する運用画面。
- **延長対応（押え）／早終い（巻き）**：生番組の延長は後続番組を繰り下げ＋フィラー隙間で吸収（解決窓内に限定）、短縮は隙間をフィラーで自動充填。明示の押え操作が無ければ既定どおり強制カット。
- **通知基盤**：webhook（Discord 等）を先行実装し、Zabbix 等は同一インタフェースで後付け可能とする。

### 利用ロール

利用者ロールを以下に確定した（画面別の権限マトリクスは [ui.md](ui.md)）。
- **内部 5 ロール**：管理者 / 運用者 / 営業 / 経理 / QC担当。
- **外部の制作会社**：社内シェルを持たず、組織スコープの納品ポータルのみを使用する。
